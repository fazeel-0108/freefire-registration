2 · YouPI suitability — what its own repository says

Red flags you should weigh

  • Experimental by declaration. README: research/learning only, no warranty, “not for critical payments”.
  • No compliance claim. “Using this software does not itself authorise you to operate a payment aggregator” — RBI/NPCI/bank rules are your responsibility.
  • Conservative project limit: ≤ 20 payment attempts per day per receiving account for experiments.
  • Verification is observational — bank SMS on a phone + Gmail alert, not a bank API. Level 2 means both agreed, not that a bank certified it.
  • Licence is ambiguous. README points to a LICENSE file that does not exist; package.json says "license": "Commercial".

What is actually strong in it

  • Money moves directly to your UPI account; no aggregator holds funds.
  • Merchant-private data needs X-Merchant-Key; anonymous callers get a redacted view.
  • verificationLevel is only returned to the owning merchant, so an unauthenticated read cannot fake “level 2”.
  • Developer/test endpoints are refused when NODE_ENV=production unless YOUPI_ALLOW_DEV_TOOLS=true.
  • Our server holds sub-level payments for an organiser instead of registering the team.

3 · Isolated sandbox — yes, but not by flipping test mode on production

YouPI’s test tooling is real: POST /api/v1/admin/dev/test-mode (10-minute window, disables auto-banning for that merchant, audited) and POST /api/v1/checkout/:id/simulate-observation (injects a synthetic SMS into the real verification pipeline).

Do not use either on the gateway that will take real money. Two consequences matter:

  • Test mode turns off auto-banning for the merchant for ten minutes — a security control, disabled by design.
  • simulate-observation can settle live sessions. It is gated by the admin token, but enabling it on production means one leaked admin token can mark payments paid.

Safe isolation instead:

  • Separate YouPI instance — own database, own ports, NODE_ENV=development, no bank observers attached, a throwaway merchant with an unused test VPA. Nothing it does can reach the production ledger.
  • Separate Apps Script project — a copy of the code with its own Script Properties, pointing at the test instance.
  • Separate sheet — a copy of the production sheet, never the production file.
  • Direct API calls — do not repoint the public site at the test deployment; call the staging /exec from a local page.

5 · The merchant-identity gap — and the smallest safe fix

What the gap is. YouPI never returns merchantId in a payment response — not in CreatePaymentResponse and not in PaymentDetailsResponse. So “compare the merchant in the response” cannot be implemented as written. Identity is currently established only by the credentials we send.

How it can bite. A non-owner read returns a redacted view with no verificationLevel. Our code does Number(session.verificationLevel) || 0, which turns “not ours / not owner” into level 0 → status NEEDS REVIEW. A team is not registered automatically, which is safe — but an organiser could later accept it by hand on a payment that never reached our account.

Smallest safe fix (3 lines, in verifyYoupiPayment_, no schema or deployment change): treat a missing owner-only field as a failed identity check rather than as “level 0”.

var level = session.verificationLevel;
if (level === undefined || level === null || level === '') {
  // No owner-only field: this response is not the owning merchant's view.
  return { state: 'MISMATCH', reason: 'identity', provider: 'YOUPI',
           paymentId: cleanText_(session.paymentId) || draft.paymentId };
}

Existing tests already return verificationLevel on every SUCCESS reply, so this is compatible with the 566-test suite. A stronger optional step is also checking that session.metadata.token equals the draft token — YouPI returns metadata only to the owner — but that needs the test harness to echo metadata and is a slightly larger change. I have not applied either; code is untouched.
